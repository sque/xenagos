# diff-browser Specification

## Purpose
The browse mode: lets the reviewer read the whole change freely, with files grouped so that hand-written code is not
buried under tests and generated files, and with the full file available wherever context is needed.

## Requirements

### Requirement: File tree with categories
The viewer SHALL list every changed file and SHALL place each in exactly one category: Code, Tests or Generated. Lock
files and files marked generated by repository attributes SHALL be Generated. The tree SHALL show per-file added and
removed line counts and per-category totals.

#### Scenario: Lock file
- **GIVEN** a change that touches `src/app.py`, `tests/test_app.py` and `uv.lock`
- **WHEN** the review opens
- **THEN** the three files appear under Code, Tests and Generated respectively

#### Scenario: Category correction
- **WHEN** the reviewer moves a file to another category
- **THEN** the file stays in the chosen category for the rest of that review

### Requirement: Folders are kept inside each category
Within each category the files SHALL be shown as a tree under their folders, with the cues customary for a file tree,
and SHALL NOT be shown as a flat list of paths. A folder SHALL appear in a category only when it holds a file of that
category.

#### Scenario: Two files in one folder
- **GIVEN** the change touches `scheduler/batch.py` and `scheduler/settings.py`, both Code
- **WHEN** the review opens
- **THEN** Code shows one `scheduler` folder holding both files

#### Scenario: Folder split across categories
- **GIVEN** the change touches `pkg/core.py` (Code) and `pkg/core_pb2.py` (Generated)
- **WHEN** the review opens
- **THEN** `pkg` appears under Code holding `core.py` and under Generated holding `core_pb2.py`

### Requirement: Generated files stay out of the way
Files in Generated SHALL be collapsed by default and SHALL be openable on demand.

#### Scenario: Large lock file
- **WHEN** a review containing a 4,000-line lock file change opens
- **THEN** the lock file's diff is not rendered until the reviewer opens it

### Requirement: Diff display
For each file the viewer SHALL show the diff in unified or side-by-side layout, switchable by the reviewer, with syntax
highlighting. Renamed, added, deleted and binary files SHALL be labelled as such.

#### Scenario: Layout switch
- **WHEN** the reviewer switches from unified to side-by-side
- **THEN** every open file re-renders side by side and the reading position stays on the same file

### Requirement: Full-file expansion
The reviewer SHALL be able to expand any changed file from its hunks to its full content at the head
revision, with changed lines still marked, and to collapse it back. Expansion SHALL also be possible in steps around a
single hunk.

#### Scenario: Expand whole file
- **GIVEN** a file with two hunks 300 lines apart
- **WHEN** the reviewer expands the file
- **THEN** all lines of the file are shown in order and the two hunks keep their added and removed marking

### Requirement: Per-commit view
When the target spans several commits, the reviewer SHALL be able to switch between the combined diff and the diff of
any single commit, with that commit's message shown.

#### Scenario: Pick one commit
- **GIVEN** a range of three commits
- **WHEN** the reviewer selects the second commit
- **THEN** the tree and diffs show only what that commit changed, under its message
